# FastIOT 产品规格评审

日期：2026-11-13。代码基线：eff9231。

评审对象：[已发布产品规格的本地正文](specs/2026-11-13-open-scada-paid-ems.md)，以及相关目标、术语和旧规范。评审只输出建议，不修改产品实现、已确认目标或 GitHub Issue。

## 结论

**目标方向成立，主规格仍应视为产品总规格，不宜直接当作一张可一次实现的任务。缺的主要是验收闭环和少数产品行为，不是更多模块。**

优先补齐：每个样板自身的完整交付证据、AI 修改的真实可用性、修改后旧检查结果的适用性、回滚时运行参数兼容、离线故障恢复的授权含义。

优先简化：主文按用户旅程组织，62 条故事保留为追踪清单，26 组验收保留为矩阵；不要把每条故事实现为独立页面、独立状态机或独立服务。跨文档的冲突声明应先统一。

本报告中的建议分为三类：**既有目标的必然补全**、**需要产品方选择的行为**、**留给实现设计的细节**。新增选择不冒充已确认决定。

## 已核实的跨文档与商业问题

### R1 — 多份文档仍声称拥有最终解释权（优先修正）

**证据：**

- [旧 v1 规格](product-spec-v1.md:3) 声称“当前唯一权威”。
- [任务合同](jobs.md:5) 声称是“完成”的唯一判据，并要求冲突时以它为准；[同一文档](jobs.md:42) 仍规定运行页只读，[完成定义](jobs.md:48) 仍把旧黄金路径通过及耗时未回退作为判据。
- [总目标](../GOAL.md:23) 仍把旧任务合同作为准入依据，并将项目包导出／应用生成与其他条目一起列作未被具体任务要求的未排期项。
- [旧最终说明](no-code-platform-final.md:15) 把发布描述为自动完成迁移与部署，与已确认的动作区别不一致。
- [README](../README.md:5) 已指向新规格，但后续仍保留旧冻结范围入口，没有统一标识其历史适用范围。

**后果：** 人或 agent 从不同入口读取，会合法地得出相反的实现范围。新增一份更长的规格无法解决这个问题。

**建议：** 明确新规格为当前产品目标与验收依据；旧文档添加历史状态和被替代条款指针，保留历史证据，不删除曾经通过的结果。不再让旧任务合同覆盖新的独立 SCADA、运行调参及项目包要求。

**可直接采用的条款：**

> 本规格对应当前目标。旧 EMS-only 范围、只读客户工作台及导航可达性验收只描述历史阶段；不覆盖本规格。已有安全不变量和真实测试证据按其原始适用范围保留。

分类：已确认目标的一致性修正，不需要重新决定产品定位。

### R2 — 付费包的许可边界需要具体化，不能仅写“另行核查”

**事实：** 仓库根目录 [LICENSE](../LICENSE:66) 与 GitHub 元数据都显示 Apache-2.0。其第 2 条授予符合条款的永久、免费和不可撤销的版权许可；第 4 条要求分发保留许可及适用声明，也允许在满足原许可义务的前提下为自己的修改或衍生作品提供不同条款。上游 Simple IoT 的许可证同样是 Apache-2.0。这不是完整依赖审计或法律意见。

**后果：** 不能通过在新版本加授权按钮，撤销已公开 EMS 代码接收者原有的使用权。另一方面，Apache-2.0 并不等于不能收费或不能开发商业增量。

**建议：** 在商业发布前补一张分发清单，区分既有开源底座／既有 EMS 代码、未来商业增量、厂商 Profile 与素材、打包依赖。明确各自权利来源、许可和随包声明。具体商业包增量由产品方选择；不要为了授权提前设计复杂 DRM。

**可直接采用的条款：**

> 已按 Apache-2.0 发布的代码继续遵守原许可。生产实例授权约束商业包及相应商业权益，不追溯限制既有开源版本。商业包分发前完成代码、依赖、Profile 与素材的许可清单。

分类：许可事实已核实；商业增量内容属于用户决策，许可文本与权属必要时需专业审查。

## 主规格的补充与简化建议

### R3 — 每个样板必须有自己的完整交付结果，而不是拼接局部通过（优先补齐）

位置：主规格“首版可交付样板”、故事 39／40／53／61、T01／T09–10／T14／T19／T21–22／T26。

现有矩阵把换厂商、部署、调度和回滚分开描述，容易出现“泵房证明部署、储能证明调度、光储充证明约束”，最后合称全部可交付。

**建议条款：**

> 为已有验收项标明适用样板。储能与光储充分别完成换厂商、重复部署、升级和回滚；每个交付结论对应同一个项目的配置、验证、部署和交接证据，不能拼接不同项目的局部通过。

最小表达是一张“样板 × 已有验收项”勾选矩阵；不新增验收系统。不规定虚假的半天交付目标，先测真实工时和需要开发者介入的次数。

分类：既有目标的必然补全。

### R4 — AI 能生成网页，不等于交付人员能独立改好画面（优先验证）

位置：故事 11–13／19、实施决定第 4 节、T05–08。

“可运行网页”不足以验证全部由 AI 修改：应证明明确的局部改动成功、无关区域未被破坏、原有绑定和操作仍正确。失败时重新生成整个页面可能丢掉已确认成果。模型支持图片也不能证明理解了标注意图。

**建议条款：**

> 代表性验收包含首次生成、对话局部修改、标注截图修改及修改后回归；不以人工修改源码、布局或属性完成验收。失败保留上一可用版本及可继续修改的上下文，展示错误，不覆盖运行版。

建议先用少量真实 DeepSeek 调用验证文字生成、Three.js 页面和标注局部修改三种任务，记录成功与失败；执行前单独确认预算与发送内容。日常回归仍用固定响应覆盖超时、拒绝、无效代码和恶意输出。本轮未发生真实调用。

分类：验收补全已由目标蕴含；预算、代表性画面与量化合格线由用户或对应设计任务确定。不添加手工编辑器兜底，不推翻已确认的 AI-only 修改方式。

### R5 — 检查从简，但必须知道旧证据是否还适用（优先补齐）

位置：故事 43–45、实施决定第 6 节、T18。

检查后改了点位映射、规则或画面，原来的通过记录不能永久有效。也不能反过来要求一次软件打包必须先完成所有真机验收。

**建议条款：**

> 同一问题清单说明证据所对应的工程版本、现场绑定与验证范围。相关对象改变后，受影响项目提示重新检查；无关证据可保留。不把仿真记为真机，不新增第二套清单，检查不启动设备。

只需记录关联依据并显示失效原因，避免提前做通用依赖计算引擎。具体每类修改影响哪些检查，应写成简短规则表。发布、部署、启动控制原有必要校验继续存在，但不能重新包装成用户否决的两套门槛。

分类：既有目标的必然补全；实现细节后定。

### R6 — 回滚工程时，也要检查运行参数（必须补齐）

位置：故事 46／48／50／52、实施决定第 5／7 节、T20–22。

当前对运行参数兼容的明确描述集中在升级。若新版开放的参数超出旧版允许范围，只回滚工程定义可能留下不兼容的现行参数。

**建议条款：**

> 回滚校验目标工程版本与现行运行参数的兼容性；不兼容值明确处理后才能恢复控制，不静默沿用或改值。历史保持追加，仍能查明当时工程版本与有效参数。

必测例：新版允许、旧版禁止的参数值在回滚后不得成为未经确认的控制依据。不要把“保留历史”误解成“任何当前参数都必须无条件保留”。

分类：既有恢复目标的必然补全，不新增审批流程。

### R7 — 到期后的同现场恢复不能被误判为新增部署（必须澄清）

位置：故事 59–60、实施决定第 9 节、T23–25。

“到期限制新增部署”与“故障换机可以迁移”并存，但分类仍有歧义：原机坏了、断网、授权已到期时，系统可能禁止重装已授权版本。

**建议条款：**

> 同一已授权现场恢复既有授权版本，不视为新增生产部署；不因此获得并行运行权。恢复验收包含原机不可用、无法联网且更新权益已到期的场景。

需要产品方决定的不是要不要停机收费，而是：**完全离线且原机不可用时，如何兼顾恢复与防复制**。产品承诺可以先明确，技术与服务机制后定；纯离线软件不能凭空保证旧实例已永久停用。不要为此提前建设强 DRM 或偷加在线依赖。

分类：持续运行承诺的补全；恢复保障与反复制取舍需要产品方确认。

### R8 — 客户的日常闭环与运行数据导出不能被工程包导出替代（应补齐）

位置：Problem Statement、故事 54–55、T01／T17／T26。

“报警出现”和“权限拒绝”不是完整客户作业；“导出了项目包”也不是能导出运行历史。

**建议条款：**

> 在不安装 EMS 的样板中，操作员独立完成报警定位、授权处理、查看设备反馈和历史追溯；获准用户能导出其授权范围内的运行历史，不以购买 EMS 为前提。

合并到既有样板、权限和独立试用验收即可，不新建报表中心，不增加付费数据解锁。

分类：已承诺底座用途的补全。

### R9 — 运行规则不能留给开发者猜，但不必重新访谈所有已定案内容

位置：故事 34／38、实施决定第 8 节、T09／T12。

[既有控制定案](control-chain-decision.md:26) 已确认人工接管停止自动、显式恢复；[补充定案](control-chain-decision.md:60) 已要求提交后样本关联，并明确恢复前重新读状态且不重放旧命令。不能把这些重新列成未决定。

仍需在相关实施任务前明确的少数结果：资源组／站级计划处于同级时如何解决冲突；接管某个 EnergyUnit 后，其他来源如何报告被抑制及剩余资源不足；恢复自动采用哪些当下有效输入。这些会改变实际控制结果，必须有场景与预期，而不是“实现前自行处理”。

**建议：** 补一张小型冲突／恢复场景表，复用已有仲裁与追溯，不引入另一套调度框架。保留安全约束始终有效、无自动原命令重试和无旧命令重放。

分类：既有规则先继承；尚未约定的同级冲突与恢复细节需产品／领域决策。

### R10 — “bin”不是应随便删除的术语，应补回已有定义

位置：故事 33、实施决定第 8 节、T11。

独立评审指出“缺 bin”在新规格中没有定义，属实；但核查 [2026-11-11 定案](control-chain-decision.md:74) 后，不能把它当成任意实现细节删除。已有定义是 `(t-15min, t]` 的窗口、1 分钟滑动、15 个一分钟分段、各段至少一个新鲜有效样本、先段内平均再段间平均。

**建议条款：**

> 需量按已有窗口与一分钟分段规则验收，缺段时说明缺样区间并停止缺少依据的预测性削峰；独立安全限制继续有效。用跨窗口回放验证，不把固定窗口平均当作滑动需量。

用户界面用“缺少某一分钟的数据”等可理解的文案，不把 bin 术语推给操作员。保存这一语义不意味着必须采用某种特定内存数据结构。

分类：补回既有定义，不增加新的算法决定。

## 外部资料核实与最小验证

完整来源与证据范围见 [官方资料核查笔记](spec-review-sources-2026-11-13.md)。以下区分已核实事实与建议验证，不把文档支持当作运行效果。

| 事项 | 核查结论 | 规格应补充的最小结果 |
| --- | --- | --- |
| DeepSeek 图片输入 | 官方 Vision 文档支持 `deepseek-flash` 图片输入；不代表任意 DeepSeek 模型都支持，也不保证标注编辑效果 | 用真实模型验证文字生成、标注局部修改与绑定保持；固定响应回归另算。模型名称／别名变化不应影响已交付产物 |
| 生成网页的隔离 | MDN 明确警告同源 iframe 同时启用 `allow-scripts` 与 `allow-same-origin`；sandbox 不是禁网保证，代码净化不替代执行隔离 | 预览和已发布画面都不能读取宿主凭据、访问越权对象或绕开受控命令；恶意代码、伪造消息和页面重载均有负向测试 |
| 受控宿主通信 | postMessage 提供通信，不提供授权；需核对来源／发送窗口与消息结构，特殊来源不能只靠字符串 `null` 判断可信 | 页面只能获得本项目获准的数据和操作能力，撤销权限／页面失效后的旧请求不能继续执行，后端仍逐次鉴权 |
| Three.js | 当前 WebGLRenderer 使用 WebGL2，r163 起不支持 WebGL1；不保证所有工控机及帧率 | 固定目标浏览器／驱动／硬件后测渲染与资源使用。WebGL2 不可用或上下文丢失时明确提示，不能仍显示貌似正常的控制画面 |
| 离线资源 | 已确认需求是固定离线产物，但本次官方安装正文的访问失败，未据此声称自动打包全部资源 | 冷缓存断网安装，检查脚本、addons、模型、纹理、字体、解码器及 worker 实际网络请求。断网运行通过才是证据，lockfile 本身不是 |
| Modbus RTU | 官方串行规范定义 RTU 帧间隔、CRC、地址及 RS485 电气要求；PTY 只能覆盖其中的软件协议部分 | 软件走正式串口路径注入坏帧、延迟和断线；物理链路另外测方向切换、电气与时序；目标设备反馈再单独验收 |

### 应丰富的安全条款，不是新增安全平台

建议把“生成网页经过预览”补成：

> AI 生成代码始终视为不可信，预览和正式运行都受相同的权限与数据访问约束。通过检查或人工确认不能赋予其宿主会话、设备凭据或任意网络访问能力。画面失败、卡住或 WebGL 上下文丢失时不伪造设备正常；设备保护和命令权限继续由可信运行逻辑执行。

构建阶段也不能因为输出是前端代码就被视为无害：依赖安装和构建脚本不得继承生产凭据或挂载运行数据。具体隔离方法留给设计，产品规格只规定不可突破的结果，不锁定某种新常驻服务。

这不要求禁止 AI 生成网页，也不要求改回 JSON-only 组态；它补齐了已确认“网页不能绕过平台安全”的可测含义。

## 建议的规格结构

不推倒重写，也不靠增加用户故事数量体现“丰富”。建议主文保留六条旅程，原有编号作为附录追踪：

1. 空白项目接入设备，形成可解释数据与命令。
2. AI 生成画面、对话修改、标注修改及失败保留。
3. 一个入口检查、确认、离线交付给另一位人员。
4. 客户日常报警、操作、运行调参、历史追溯与导出。
5. 工程升级、处理冲突、失败回滚和故障恢复。
6. 在同一底座加入 EMS 包，完成储能和光储充样板。

附录 A 保留 62 条故事作为追踪索引；附录 B 保留并补齐 26 组验收的样板适用关系；附录 C 列出尚未验证的外部前提与主张范围。不要把总规格的 `ready-for-agent` 理解为全部工作已具备直接实现条件；它是父规格，各实现任务需有自己的完整行为和验收。

### 明确该减的东西

- 删除旧文档与新规格互相争夺“唯一权威”的声明，而不是删除历史证据。
- 减少主文反复解释同一个原则；故事、约束与测试通过编号关联，不再复制三份长说明。
- 一个项目保留当前版本、草稿和可恢复版本的必要信息即可；不要从“版本化”推导出 Git 式分支、多人会签或审批链。
- 冲突显示必要差异并人工选择；不要因为三方对照就先做通用自动合并引擎。
- 一张交付问题清单即可；证据适用性不必做成另一套发布／投运状态机。
- 首版以现有协议、一个 AI 提供方和明确样板证明深度；不建设多模型市场、热插拔框架或未出现行业的插件体系。
- 把当前代码缺陷作为现状与对应任务依据，不让长期产品规格绑死某个函数名、页面名或文件结构。

### 应先取得的证据

这不是实施排期，也未执行以下试验；它们用于降低随后拆票的猜测：

- **真实 AI 修改闭环：** 首次生成、两轮局部修改、原绑定回归；需单独授权调用预算。
- **生成代码隔离：** 在不接真机的环境验证宿主凭据隔离、受控读写、旧页面失效和明确错误反馈。
- **RTU 行为样板：** 根据声明的设备状态与时序，证明命令、拒动、反馈、断线恢复均穿过正式串口路径。

完成这些证据不等于三个产品样板全部验收；它们只回答“核心交互是否做得成、最危险的假设是否成立”。

### 还需要产品方决定的范围

不用再重复 28 轮目标访谈。保留少数真实选择到对应任务前确认：

1. 既有 Apache-2.0 EMS 能力之外，具体哪些商业增量／权益构成付费包。
2. 同级调度目标冲突及人工恢复自动的未约定细节；已确认的安全优先、不重放旧命令不重问。
3. 到期且原机失效时，完全离线恢复保障与防并行复制的现实取舍。
4. 真实 AI 试验预算、目标工控机／浏览器及基于实际样板确定的合格线。

其余一致性和验收补全可以按已有决定修订，不应再把普通工程选择推给用户。
