# v1 开发瓶颈与待补功能建议

日期：2026-11-06
范围：FastEMS v1 软件侧；不含真实设备签收（M5）。

## 1. 当前真正的开发瓶颈

1. **反馈回路太长**：每次前端改动都要 `npm run build` 写入 `internal/web/dist`，再用 Docker 编 Go 二进制；改样式和交互时大部分时间花在重建上。
2. **前后端类型靠手写同步**：`frontend/src/api.ts` 的 DTO 与 Go struct 分开维护，字段改名/新增时只能靠编译和浏览器回归发现。
3. **现场协议依赖模拟器且模拟器太简单**：当前 TCP 模拟器只有寄存器 0/10/11，缺少异常码、超时、断线、不同站号/功能码的可配置注入；很多 M5 前的异常路径无法稳定复现。
4. **核心语义尚未全部接线**：命名命令引擎、审计、通信质量统计等已有局部实现或基础数据，但产品入口不完整（见第 3 节）。
5. **大文件与重复验证脚本**：`App.tsx` 779 行、`styles.css` 2359 行；浏览器脚本各自复制登录和页面导航，改一处要同步多处。
6. **真实设备不可替代**：Profile 常量、地址/缩放/字序、RS485 现场行为只能靠 M5；软件侧能做的是把模拟和证据工具做好。

## 2. 建议引入的工具/实践

| 优先级 | 引入项 | 解决什么 | 成本 | 说明 |
| --- | --- | --- | --- | --- |
| P0 | Vite dev server + Go 热重载（air 或等价） | 已接入 Vite 代理与 dev 脚本 | 低 | 生产由 Encore 提供；仅开发模式加 `/api` 代理 |
| P0 | `tygo` 或等价 Go→TS 类型生成 | 已接入 `contract` + generated 类型 | 低 | `scripts/gen-types.sh`；不引入运行时 |
| P0 | 可配置 Modbus 模拟器 + 故障注入 | 已接入 JSON fixture 与故障参数 | 中 | 寄存器/线圈/延迟/破坏/断线；覆盖 Profile 与安全路径 |
| P1 | 一条 `make verify` / PowerShell 验证入口 | 已接入 `scripts/verify.sh` | 低 | 统一 Go test/vet、构建、browser-smoke、layout-check、theme-check |
| P1 | `golangci-lint` / staticcheck | 提前发现未使用代码、错误处理遗漏 | 低 | 与现有 `go vet` 互补 |
| P1 | 前端页面拆分 + `usePolling` 等共享 hook | 降低 `App.tsx`/样式回归风险 | 中 | 不引入状态库；先拆页面和轮询 |
| P1 | 共享 Playwright 登录/导航 helper | 减少脚本重复与维护成本 | 低 | 现有 layout/browser/主题脚本共用 |
| P2 | 请求 ID + 结构化日志 | 串联一次控制/报警/规则求值 | 中 | 与审计/报文查看器共用基础设施 |

不建议引入：SQLite 第二存储（v1 无必要）、React Query/Storybook（当前规模不划算）、替换决策表引擎。Encore 已于 2026-11-06 变更为生产运行时，见 [`encore-migration.md`](encore-migration.md)。

## 3. 待补功能列表（按 v1 完成度）

### P0：不补就不能说 v1 软件侧完整

1. **命名命令执行链路（V1-3）——固定值与参数化命令已实现（2026-11-06）**
   - 现状：`internal/ems/command` 有幂等提交、回读、超时/unknown 状态和测试；`runtime.NewService(nil, ...)` 没有 Profile 解析器，也没有 HTTP/UI 入口。Profile 里的命令目前只能看数量，不能执行。
   - 要补：设备/Profile 绑定持久化；命令 API（提交、查询状态）；设备/点位详情的命令参数与执行反馈；读回、超时、结果未知、重复提交测试。
   - 为什么优先：这是 v1 明确能力，也是 PCS/BMS 现场控制的必经路径。

2. **审计日志（V1-10 / V1-8）——已实现（2026-11-06）**
   - 现状：Point 有 `origin`、`lastCommand` 等底层痕迹，但没有独立审计记录、查询 API 或页面。
   - 要补：登录、配置变更、控制命令、报警确认、规则发布五类；操作人/动作/对象/结果/IP/时间；筛选与 CSV；保留上限。
   - 为什么优先：验收报告把审计写成通过，口径偏宽；现场追责需要可读记录。

### P1：现场可用性与 M5 准备

3. **原始报文查看器**
   - 按通道/设备查看收/发 HEX、时间、对端；暂停、清空、复制、重连。运行时做有界环形缓存，不改变采集路径。
   - 价值：站号、地址、CRC、超时现场排查；也是 M5 证据工具。

4. **通信质量统计（V1-11）——已实现（2026-11-06）**
   - 现状：通道有 `lastGoodPoll`/`errorCount`，没有成功率、延迟、按设备/点位的质量趋势。
   - 要补：轮询成功率、平均/最大延迟、错误分类、按通道/设备的时间窗口统计。

5. **历史保留上限可配置（V1-8）——已实现（2026-11-06，持久历史重启生效）**
   - 现状：`runtime.NewService(..., 20000)` 硬编码；没有 UI/配置。
   - 要补：站点级保留上限、历史查询上限提示、清理策略；避免长时间运行后内存/查询压力。

6. **分配器目标嵌入规则编辑器**
   - 现状：分配器配置页和 API 已完成，规则行只能绑定普通点位，分配器目标要在 API/文档层绑定。
   - 要补：规则输出行的目标类型选择（点位/分配器），校验和 `lastCheck` 解释。

7. **报警声音/静默/维护/统计**——已实现（2026-11-06）
   - 声音、音量、试听、静默时段；维护期抑制已知告警；今日/昨日、7/30 天趋势、设备排行。
   - 纯本地，不引入通知组/邮件/短信。

8. **设备级健康汇总与 Profile 验证记录**——Profile 验证记录已实现（2026-11-06）
   - 通道页显示端口健康，点位有 health；缺少按设备的健康汇总和“Profile 已现场验证”的证据记录（验证人/日期/设备序列号/点位核对结果）。
   - 价值：M5 签收和交付边界更清楚。

### P2 / v1.1

- 报表模板：历史报表、用能报表、Excel 模板导出。
- Profile 展示：变量模型/控制能力分栏（参考 ThingsPanel 物模型）。
- 时间窗口/周期触发：峰谷、星期、跨午夜；当前 v1 明确不做。
- 场景模板、策略模板、自由拖拽画面：v1.1 或不做。
- OTA、通知组、数据转发、工单、云多站：超出单机离线 EMS。

## 4. 建议实施顺序

1. 命名命令执行链路（P0，v1 能力缺口）
2. 审计日志（P0，v1 能力缺口）
3. Vite dev + tygo + 模拟器故障注入（P0，开发效率）
4. 报文查看器 + 通信质量统计（P1，M5 现场）
5. 历史保留配置 + 分配器目标入编辑器（P1，v1 完整度）
6. 报警声音/维护/统计、设备健康与 Profile 验证记录（P1）
7. 报表模板、Profile 分栏（v1.1）

## 5. 约束

- 不引入第二业务服务、云端或外发通知；Encore 作为唯一生产运行时，见迁移文档。
- 不把真实设备验证替换成模拟器；模拟器只做回归。
- 新工具只进入开发/验证链路，不进入生产运行时。
- 每个 P0/P1 功能都要有失败路径证据：超时、重复提交、越权、断线、过期。
