# FastIOT 任务合同

版本：2026-11-12 · 状态：**历史任务合同，范围及完成口径已被替代**。

当前目标、权限和验收以 [FastIOT 产品规格](specs/2026-11-13-open-scada-paid-ems.md) 为准（本地评审修订暂未同步 GitHub）。下文保留旧 EMS 导航与任务组织记录，不得据此要求独立 SCADA 项目配置能源对象，或禁止客户执行已授权操作及运行调参。历史脚本通过不代表当前产品可交付。

## 1. 任务模型

买家是反复交付 EMS 项目的团队。一次交付由六个任务组成，顺序固定；每个任务只有一个归属界面，界面内部的步骤可以有多页签，但入口只有一个。

| 任务 | 一句话 | 归属界面 | 进入条件 | 退出条件（可验证） |
|---|---|---|---|---|
| J1 接入 | 把现场设备接进来 | 接入 → 通道 | 项目与站点已建 | 每条通道运行；每台设备绑定 Profile；关键点位有未过期值；预检 `channels`、`points` 无 fail |
| J2 能源设备 | 把设备组织成可调度的储能单元并验证 | 能源设备 → 储能柜 | J1 退出 | 每个单元绑定设备与功率点位；能力显示充/放可用功率与新鲜 SOC/温度；设备台账全部“已验证”；预检 `commands`、`manual`、`disabled` 无 fail |
| J3 策略 | 决定什么条件下怎么动作 | 策略 → 决策表 | J2 退出 | 决策表已发布；试算逐台给出动作、原因与胜出来源；预检 `rules` 无 fail |
| J4 试运行 | 证明“请求 → 下发 → 回读 → 实测”闭环 | 运行 → 调度追溯（从总览进入） | J3 退出 | 至少一条追溯同时有 request_id、下发、回读与实测；超时显示“结果未知”且不自动重试 |
| J5 交付验收 | 把项目交给客户或下一位同事 | 交付验收 | J1–J4 完成 | 预检全部 gate 无 fail（`backup` 为提示项）；版本已冻结；证据含操作者与时间；遗留项明确 |
| J6 运维 | 交付后的日常与售后 | 运行 → 报警 / 系统 → 审计 | 已交付 | 任一报警、控制或配置可追溯到操作者与对象；回退后可继续使用 |

客户侧只有两个任务：

| 任务 | 归属界面 | 说明 |
|---|---|---|
| R1 看运行 | 运行 → 总览 / 画面 / 报警 | 三个页签；未接入或过期的值显示“—”，不生成数据 |
| R2 查历史与追溯 | 从总览、画面、报警内的链接进入 | 不作为一级导航；历史、调度追溯、通信健康都属于“查证”，不独立成为任务 |

## 2. 页面归属（唯一入口）

| 任务 | 一级入口 | 页签 | 明确不放在这里的 |
|---|---|---|---|
| 接入 | 接入 | 通道、点位表、聚合计算、OPC-UA | 能源单元、策略、验收 |
| 能源设备 | 能源设备 | 储能柜、接线、资源集群 | 通道参数、决策表 |
| 策略 | 策略 | 决策表、功率分配器 | 单元绑定、设备参数 |
| 交付验收 | 交付验收 | 验收清单、设备验证 | 日常运行画面 |
| 系统 | 系统（仅管理员） | 账号与权限、审计日志 | 业务配置 |
| 运行（客户） | 运行 | 总览、画面、报警 | 任何配置入口 |

规则：

1. **一个对象只有一个配置入口。** 点位只在“接入 → 点位表”配置；其他页面只能链接过去，不得复制一套编辑表单。
2. **导航按任务分层，不按后端模块分层。** 通道、点位、聚合、OPC-UA 不是平级任务，是“接入”的页签；分配器是“策略”的内部机制，不单独成为任务。
3. **旧运行页只读约定已被替代。** 当前按权限开放客户操作与运行调参；工程修改仍走草稿，具体以新规格为准。

## 3. 功能准入与删除

任何新增或修改，提交说明必须写清：**服务于哪个任务、缩短了哪一步、退出条件是否仍可通过**。写不出任务的改动不做。

- **历史完成定义已被替代**：旧 `frontend/golden-path.mjs` 及其耗时只作为历史冒烟检查记录，不证明当前样板可交付。当前完成判据以新规格的用户旅程、样板适用关系和行为验收为准。
- **删除优先**：没有任务归属的页面、面板、入口，在一个发布周期内删除或隐藏；不保留“以后可能有用”的界面。
- **架构覆盖不是路线图**：模块图上的未实现项，只有被具体客户任务要求时才排期；不得因为“图上有”而补界面。
- **证据边界**：模拟器与真实设备分开记录；模拟器通过不替代现场签收。

## 4. 黄金路径

`scripts/golden-path.sh` 启动一个隔离实例（独立数据目录、随机管理员密码、不接触演示库），由 `frontend/golden-path.mjs` 驱动以下历史冒烟步骤，记录耗时与预检结果，输出 `evidence/golden-path.json`。这些步骤主要检查页面可达、预览和冻结，不能证明 J1–J5 已完成，更不是“能不能交付”的唯一判据：

1. 登录并进入交付验收，读取当前阻断项；
2. 从已验收项目复用预览，列出待确认项；
3. 接入页确认通道与点位表可到达；
4. 能源设备页确认储能柜可到达；
5. 策略页确认决策表可到达；
6. 运行预检，记录各 gate 状态（`blockingGates`、`deliveryReady`）；
7. 冻结版本，记录证据与耗时。

报告里的 `status` 只表示这些脚本步骤是否跑通；`deliveryReady` 仅由旧门槛是否含 fail 推导，不能证明站点可投运。演示种子实例的阻断与测试结果按原样保留，不为了跑绿而伪造。

历史设想的“半天预检、30 分钟交接”没有完整任务基线，不能作为已兑现承诺或本轮验收门槛。新规格要求记录实际工时、阻塞与开发者介入，再确定有依据的目标。

## 5. 角色与任务

| 角色 | 可执行任务 |
|---|---|
| 实施/集成 | J1–J6（系统任务仅管理员） |
| 操作员 | R1、R2；J6 中的报警处理 |
| 只读 | R1、R2 |
| 管理员 | 全部，含账号与审计 |

角色可见性只减少误操作；能否读写仍由服务端按业务树范围逐请求判定。
