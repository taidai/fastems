# 参考系统功能评审

日期：2026-11-06
范围：PowerVision 智慧电力监控系统、SSIoT 三三物联网云平台
目的：只记录可借鉴的功能设计与不适用项，不复制第三方系统代码或数据；访问凭证不写入本文件。

## 1. PowerVision 智慧电力监控

结构：顶部一级菜单（监控中心、设备管理、数据分析、图纸管理、资产管理、系统设置）+ 左侧二级菜单 + 高密度表格。与 easyems 的现场监控定位最接近。

### 值得借鉴

1. **审计日志**
   - 记录登录、退出、控制命令、告警确认、用户/角色管理等动作。
   - 字段：ID、操作人、动作、对象、详情、结果、IP、时间。
   - 支持按操作人、动作、结果、时间范围筛选，导出 CSV。
   - 对 easyems 的价值：v1 明确要求“配置与控制留痕”。当前 easyems 只有 Point 的 `origin`/`lastCommand` 等底层痕迹，没有面向人的审计查询。应补一个本地审计页，而不是只靠点历史。

2. **设备级“报文”查看器**
   - 设备台账每行提供“详情 / 数据 / 报文”三个入口。
   - 报文窗口展示时间、方向（收/发）、报文 HEX、对端；支持全部/收/发过滤、暂停、清空、复制、重连。
   - 对 easyems 的价值：现场调试和 M5 签收时，能直接看到 Modbus 原始帧，比只看“离线/错误数”更快定位站号、地址、CRC、超时问题。建议在运行时增加有界帧缓存，按通道/设备过滤，前端轮询或 WebSocket 展示。

3. **报警声音与静默时段**
   - 声音提醒开关、音量滑杆、试听；静默时段；不同告警类别（设备告警、设备故障、开关变位、程序启动、错误）分别开关。
   - 区分“设备上传告警”和“平台触发告警”。
   - 对 easyems 的价值：本地 HMI 值班场景需要声音；可实现为纯前端 Web Audio 提示 + 本地静默时段设置，不引入云通知。

4. **告警统计**
   - 今日/昨日未处理、已处理数量；7 天/30 天趋势；设备告警排行。
   - 对 easyems 的价值：现有报警页偏“列表”，缺少值班视角的统计。可在本地对报警历史做聚合，不新增存储。

5. **报表组**
   - 历史报表：多个报表卡片，各自查询、配置、导出、全屏。
   - 用能报表：按小时差值统计用能。
   - 高级报表：基于 Excel 模板的占位符报表，导出正式表。
   - 对 easyems 的价值：v1 只需要历史/报警 CSV；报表模板属于 v1.1，不建议现在扩大范围。

6. **设备台账操作**
   - 统计总数/在线/离线，按通讯状态和设备名称筛选；详情显示站点、端口 ID、设备 ID。
   - easyems 已有类似信息，但“数据”和“报文”作为设备级动作比“跳到点位表”更直接。

### 不照搬

- **单线图编辑器**：PowerVision 有完整图纸编辑器；easyems v1 明确不做自由拖拽编辑器，继续用受控的运行画面。
- **九套主题**：easyems 已确定玻璃主题与显示滑杆，不引入主题商店。
- **资产属性字典（遥测/遥信/电度/定值/压板）**：对标准化有帮助，但会增加点位模型复杂度；可作为 v1.1 的点位角色分类。
- **热重载/重启采集服务**：可借鉴“单通道重启”语义，但不需要照搬整站采集服务概念。

## 2. SSIoT 三三物联网云平台

结构：设备管理（设备/变量）、网关管理、产品管理、告警中心（监控/统计/配置）、通知中心、规则引擎（规则链）、数据转发（规则/服务）。偏通用物联网云平台。

### 可参考

1. **产品变量模型**
   - 产品详情分为变量模型、设备配置、控制功能、产品快照、可视化。
   - 变量模型定义变量标识、数据类型、名称、变量配置；控制功能单独定义可下发能力。
   - 对 easyems 的价值：现有 Profile 只有精简点位和命令 CSV；未来可在部署页把 Profile 展开为“变量模型 / 控制能力”两栏，但不要引入完整云端产品体系。

2. **变量列表**
   - 跨设备展示状态、设备、变量名、数据类型、实时值、更新时间、分组，支持按分组/设备/SN 筛选。
   - easyems 的点位表与设备数据查询已覆盖大部分；可借鉴“变量详情”入口和分组列。

3. **告警统计**
   - 今日/昨日未处理/已处理、7/30 天趋势、设备排行。
   - 与 PowerVision 的统计设计相近，可作为 easyems 报警页的轻量补充。

### 不照搬

- **规则链/规则编排画布**：节点式规则灵活但难以向现场人员解释；easyems 的有序决策表更适合“首条命中、原因可解释、可模拟”的 v1 目标。
- **通知中心（邮件/短信）与数据转发（MQTT/HTTP/DB）**：easyems 明确单机、离线、无云，不引入外发通道。
- **应用市场、API 接口文档、云多租户/分组体系**：超出 v1。
- **网关/产品/设备三层模型**：easyems 的业务树已经承担站点/设备/点位语义，再加一层产品/网关会重复。

## 3. ThingsPanel 物联网系统

结构：设备接入（设备管理、分组管理、设备模板、物模型、三方接入）、可视化（看板）、自动化（场景联动、场景管理）、告警（告警信息、通知组、通知记录）、产品管理（产品列表、OTA）、资源中心（看板模板、设备模板）、数据服务（数据转发）、工单审批、系统管理（API keys、系统日志、角色/用户）。偏通用物联网平台，覆盖面比 easyems 宽。

### 可参考

1. **设备模板与物模型分离**
   - 设备模板描述设备类型（直连/网关/网关子设备），物模型描述遥测、属性、事件和命令。
   - 对 easyems 的价值：现有 Profile 把点位和命令放在一个清单里；未来可在 Profile 详情中分成“变量/控制能力”两栏，但仍保持 CSV 导入导出，不引入完整产品体系。

2. **场景联动**
   - 卡片式列表，支持启用开关、编辑、日志、删除。
   - 触发条件覆盖设备遥测、时间范围、单次时间、每小时/每天/每周/每月周期；动作可发命令或触发告警。
   - 对 easyems 的价值：v1 决策表已经覆盖条件/动作/持续/冷却，但“周期触发/时间范围”属于 v1.1；场景的“启用开关 + 执行日志”交互可以借鉴到决策表列表。

3. **告警维护**
   - 告警信息支持详情与“维护”动作，告警配置独立；通知组支持成员、短信、邮箱、语音、Webhook、企业微信等。
   - 对 easyems 的价值：值班场景需要“维护/抑制”已知告警，避免重复打扰；通知组属于云能力，不引入。可先做本地“维护一段时间/屏蔽到恢复”的最小能力。

4. **系统日志**
   - 记录时间、IP、请求路径、方法、耗时、用户名；可按用户名、方法、IP、时间筛选。
   - 对 easyems 的价值：与 PowerVision 的业务审计互补；easyems 的审计应记录“谁改了什么”，而不是只记录 HTTP 访问日志。

5. **看板项目/模板**
   - 项目下可有多个看板，支持看板模板；可视化编辑器能力较完整。
   - 对 easyems 的价值：v1 不做自由拖拽编辑器；继续使用受控运行画面。可借鉴“项目/画面”分组和模板复制，不引入完整画布编辑器。

### 不照搬

- **完整看板编辑器**：v1 明确不做自由拖拽；当前受控画面更适合现场交付。
- **OTA 升级、升级包管理、工单审批、API keys、三方接入、应用市场**：超出单机 EMS 范围。
- **通知组/邮件/短信/语音/Webhook/企业微信**：与离线单机目标冲突；本地声音提示即可。
- **数据转发/云产品体系**：不引入。
- **设备/网关/模板/物模型四层抽象**：easyems 的业务树 + Profile + 点位已经足够，继续加层会让实施更复杂。

## 4. easyems 当前缺口（评审结论）

| 缺口 | 现状 | 建议 |
| --- | --- | --- |
| 审计查询 | 只有 Point 的 origin/命令记录，没有审计页/API | P0：补本地审计记录、筛选、CSV 导出 |
| 原始报文 | 运行时只暴露值/健康/错误数 | P1：有界帧缓存 + 按通道/设备查看 |
| 报警声音/静默 | 只有报警列表与类型管理 | P1：本地声音、音量、静默时段 |
| 告警维护/抑制 | 只有确认、关闭 | P2：维护期屏蔽已知告警，避免重复打扰 |
| 告警统计 | 只有列表与活动数 | P2：今日/昨日、趋势、设备排行 |
| 报表模板 | 只有历史 CSV 与查询页导出 | P2/v1.1：报表组、用能报表、模板导出 |
| Profile 展示 | CSV/点位清单 | v1.1：变量模型/控制能力分栏 |

## 5. 建议的 v1 收口顺序

1. **审计日志**：优先级最高，属于 v1 明确定义；先做“登录、配置变更、控制命令、报警确认、规则发布”五类，查询与 CSV 导出，保留上限可配置。
2. **报文查看器**：直接服务 M5 现场调试；先做只读环形缓存和通道过滤，不改变采集路径。
3. **报警声音/静默、统计与维护**：改善值班体验；纯本地，不引入通知中心。
4. **报表模板/Profile 分栏**：放入 v1.1，避免在真机签收前扩大范围。

## 6. 约束

- 不引入云端、外发通知、数据转发、多租户或第二套业务服务。
- 不把规则链当作决策表替代；保留首条命中与可解释原因。
- 不复制第三方主题、图纸编辑器或资产字典的完整模型。
- 审计记录不得包含密码、令牌或完整请求体；只记录操作者、动作、对象、结果、来源与时间。

## 7. Encore 评估

**2026-11-06 决策变更：生产运行时迁移到 Encore，接受 Linux/Docker 部署，不再把 Windows 单 exe 作为生产交付物。** 迁移边界、当前实现与回滚路径见 [`encore-migration.md`](encore-migration.md)。

原始评估（2026-11-05）的结论是“不建议引入”，理由仍然成立，作为背景保留：

- Encore 是“SDK + CLI + 云平台”的基础设施框架：服务/API、SQL、Pub/Sub、对象存储、缓存、Cron、Secrets 等以 Go 代码声明；`encore run` 启动本地基础设施，`encore build docker` 产出 Docker 镜像。
- 自托管需要自行提供 PostgreSQL、Redis 等基础设施，并通过配置文件注入连接；平台控制面（预发环境、可观测、自动扩缩）属于商业产品。它不是“单静态二进制、零外部依赖”的运行时。
- 这与 easyems 原来的冻结约束冲突：一个 Go 应用、单入口、离线/本机、内嵌 Simple IoT + NATS/JetStream + 前端。引入 Encore 会增加 Docker、外部数据库/缓存、工具链和新的构建入口。
- **对开发速度的实际影响**：Encore 能加速的是“从零写 CRUD/API + 数据库 + 云部署”的场景；easyems 已经自研了核心运行时，且核心是内嵌 NATS/Simple IoT 的长生命周期服务、采集循环、规则/分配器/报警 watcher，不是一组短请求 API。Encore 要求由它生成 `main`/服务结构，长运行进程和非 HTTP 生命周期需要留在框架外；即使通过 catch-all raw endpoint 增量接入，也只能加速外围 HTTP 路由，不能加速核心。

当前选择的取舍：

- 接受 Linux/Docker 交付，不再承诺 Windows 单 exe 生产包；旧 `cmd/easyems` 只保留为本地调试/回滚。
- 先用 `path=/!fallback` 原始端点让 Encore 接管 HTTP 与进程，现有路由不变；`/api/health`、`/api/device-ledger`、`/api/alarm-stats` 已迁成原生 raw 路由，再逐步迁移其余端点。
- 内嵌 NATS/JetStream 仍在同一服务内，不引入外部消息队列；当前不使用 Encore SQL，因此没有外部数据库依赖。
- 迁移成本是真实的：构建工具链、镜像、自托管运行方式和验收脚本都要换；必须用目标工控机实测，不能用 `encore run` 代替。

参考：Encore 官方文档（https://encore.dev/docs）、Encore 开源仓库（https://github.com/encoredev/encore）。
