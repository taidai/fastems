# FastIOT 策略表格：借鉴 Home Assistant 自动化的边界

> 后续定案说明（2026-11-14）：本文保留研究时的需求基线、建议和未知项，不作为最新产品契约。用户已随后确认规则求值、持续／冷却及同一请求窗口内受控重发，见[能力细则 §4](specs/2026-11-13-core-capabilities.md#已确认规则求值与计时)。文中的待定项及笼统“不自动重试”以该定案为准；HA 官方事实不因 FastIOT 的取舍改变。

研究日期：2026-11-14。目标：让交付人员会填规则、操作员能解释结果，同时不破坏现有设备控制语义。核验六组问题，引用 8 个 HA 官方正文页面（触发、条件及持续时间在官网分属不同页面）；未运行 HA、未核验 FastIOT 实现，不作版本兼容保证。

需求基线：[平台能力细则](specs/2026-11-13-core-capabilities.md) §4–6、T29/T30/T31（下称 **C**）。已读 [openHAB/HA 建议](research-openhab-ha-spec-advice-2026-11-13.md) 及 [逻辑、组态、报警与历史范式](research-logic-hmi-history-paradigms-2026-11-13.md)。前者提出的规则模板填参，当前 C §4 **已经覆盖**，不能再次包装成新增能力。以下“已有”均指规格要求，不代表实现完成。

## 结论

**借 HA 的编辑和解释方式，不借整套运行模式当设备调度器。** HA 自动化是事件触发后的条件检查与动作执行；`choose` 才有局部的有序首条匹配语义。FastIOT 的“同一行 AND、按行序首条命中”是自己的产品契约，不是 HA 或 DMN 的默认命中策略。[1][2][3][C §4]

优先补的是：何时重新求值、持续／冷却跨重启如何处理，以及真实反馈和模拟的反例。模板、统一命令入口、最新有效数值目标、泵启停特殊规则已经明确，不需要新增模式选择器或管理后台。[C §4–6]

## 1. 官方语义核验与表格映射

### 1.1 Trigger → condition → action：触发事件不是表格行

- **HA 事实：** 一个触发发生后检查条件，条件通过才运行动作；多个 trigger 是任一触发即可开始，不是全部触发凑齐。trigger ID 可供条件／动作识别来源，ID 不必唯一，省略时使用列表位置。[1]
- **条件组合：** 顶层多个条件默认全部通过，即 AND；显式 `and` 要求全部、`or` 要求至少一个、`not` 要求其中没有条件成立。条件表达的是触发后被检查的条件，不应把“现在条件成立”直接当作独立触发源。[1][2]
- **适配：** 将“为什么这次开始计算”与“这一行是否满足”分开解释；触发来源可借鉴 ID／名称的可读标识，但稳定身份沿用平台对象契约。表格继续行内 AND；不因 HA 支持组合条件就增加任意嵌套逻辑编辑器。[C §3–4]
- **反例：** 液位变化触发时，联动许可为假；之后只改变许可，是否再次求值取决于 FastIOT 的触发契约，不能仅凭“所有条件现在都真”断言必执行。多个输入发生变化也不等于多行应并发执行。[1][C §4]

### 1.2 Choose：只能类比单个有序分支块

- **HA 事实：** 一个 `choose` 选择“first option whose conditions are all met”，执行该项 sequence；没有匹配时执行可选 default，没有配置 default 就不执行默认分支。多项候选并非全部执行；而前后放两个独立 `choose`，两块可分别命中。[3]
- **具体编辑：** 在自动化／脚本编辑器加入 **Choose**，通过 **Add option** 增加条件与动作，通过 **Add default actions** 设置兜底。这种“先条件、后结果、显式兜底”的交互适合表格。[3]
- **适配：** 一次表格求值可类比一个 `choose`，每行条件对应一项候选；明确标注“按行序首条命中”，显示后续被遮蔽的满足行和未命中结果。默认行若被采用，应明确其兜底身份，不用空动作偷偷置零。[C §4；前期逻辑范式 §1]
- **边界：** 一行可提出多个动作，不代表跨设备原子执行；多张表也不能因各自选中一行就绕过同目标仲裁。不能把 HA 称为 DMN 决策表引擎，不能把 `choose` 的局部首条匹配写成“HA 默认 FIRST”。[3][C §4]

### 1.3 四种 mode：管理同一自动化的运行重叠，不管理全站设备所有权

| HA mode | 官方语义 | FastIOT 不能直接等同的规则 |
| --- | --- | --- |
| `single`（默认） | 已有运行时不启动新运行，并报告告警 | 不能变成“设备忙时所有新目标都拒绝”，否则违反最新有效数值目标及合法停机路径 |
| `restart` | 停止原运行，再开始新运行；须新触发时条件通过才重启 | 停止执行序列不等于撤销已发送设备命令，不等于 T31-E 的安全目标替换 |
| `queued` | 按加入队列顺序执行；加入时条件必须通过 | 不能证明实际下发时条件仍有效，不能默认把启动排在停机之后，也不能重放过时目标 |
| `parallel` | 新建独立运行，与旧运行同时执行 | 不授予同目标并行写权限，不能绕过人工／规则／状态机所有权与 EMS 仲裁 |

以上 mode 语义均来自 [4]；右列是对照 [C §4、T31-E/F/G/H] 的边界判断。`queued` 和 `parallel` 有 `max` 限制，默认 10；队列模式计入运行及等待数量。这是负载限制，不是安全保护。[4]

**关键区别：** HA 文档描述的是同一自动化再次触发时如何处理；不能据此推断不同自动化、人工操作与设备状态机之间有统一资源锁。FastIOT 不需让交付人员在四种 mode 中猜一个“安全模式”，而应保留既有按目标及动作类型协调的契约。[4][C §4–6]

### 1.4 `for`：持续等待不保证跨重启连续

- HA state trigger 的 `for` 要求新状态／指定属性值保持指定时间后才触发；状态改变会影响这次等待。官方明确：“the timer resets if Home Assistant restarts or automations reload”。不能写成重启后自动续上剩余等待。[5]
- 这是特定 trigger 的时间约束，不是通用持久化调度器，也不是冷却语义。该页面没有承诺把 `for` 的全部规则套用到所有条件、等待和计时器。[5]
- FastIOT 已支持持续／冷却，但 C §4 尚未明确两者在平台重启、规则重载／换版后的计时生命周期。应明确选择，不默默照搬 HA，也不能将进程离线时间当作持续取得有效现场观测的证明。[C §4]

### 1.5 Trace 与 blueprint：解释本次运行，复用输入绑定

**Trace 路径。** HA 中进入 **Settings → Automations & scenes**，从自动化菜单或编辑器顶部打开 trace；选择某次运行，点图上的节点查看 **Step details／Step config**，由 **Trace timeline** 看执行时间。运行配置可回看；默认每自动化保留 5 条 trace，YAML 自动化需要 `id` 才能保存 trace。[6]

这可映射为表格“最近一次结果 → 命中行／失败条件 → 请求结果”，而不是新增流程画布或固定照搬 5 条留存。FastIOT 需保留输入质量、持续／冷却、被抑制原因及设备结果的关联；HA trace 的运行完成状态不能替代这些业务证据。[6][C §4–5]

**测试陷阱。** HA **Run actions** 跳过 triggers 和顶层 conditions，动作序列内部的条件仍有效；手动执行没有真实触发上下文。修改实体状态或发送事件测试触发链时，官方明确 **“The actions of the automation run for real.”** 同一事件还可能触发其他自动化。它不是 FastIOT 的离线、零真实写入模拟。[6]

**Blueprint 路径。** HA 中进入 **Settings → Automations & scenes → Blueprints → Import blueprint**，输入地址、Preview 后导入；选择 blueprint、填写输入并保存，可用相同逻辑建立不同设备／参数的自动化。修改实例输入与修改蓝图本体不是同一件事。[7]

HA 的 **Take control** 会把实例变成普通自动化，此转换不可逆；修改蓝图并重载会影响使用它的自动化，重导入更新也可能需要修正不兼容输入。[7] FastIOT 只借“选模板、显式绑定、填参数”的路径；C §4 已规定实例独立、模板草稿不静默改变运行实例，不能照搬共享蓝图更新的传播方式，也不引入 YAML 或升级合并流程。

### 1.6 动作调用 ≠ 设备到位；等待表达式也不天然是物理反馈

HA 用独立的 `wait_template` 检查状态：到达等待步骤时已为真就立即继续，否则等待模板为真；可设置 timeout，`continue_on_timeout` 默认 `true`，即超时仍可继续后续步骤；`wait.completed` 才区分等待满足和超时。[8]

因此，动作后还有步骤执行或 trace 跑完，**不能单独证明设备到位**；必须看实际配置检查了什么。即使模板为真，也只证明所引用实体／表达式为真，本轮文档并未证明它一定来自新鲜、独立的机械运行反馈。[6][8]

FastIOT 已要求区分请求受理、提交、设定确认和运行反馈；本地回填、协议应答不能替代独立有效反馈。等待过程应归现有状态机／控制链路，不为了仿 HA 把任意 wait 脚本塞进决策表；超时给失败或未知的场景结果，不自动认定停机，不自动重试。[C §5、T31-A/D]

## 2. 不能退让的并发与控制基线

这些是已有规格，不是本次新增建议：[C §4–6]

| 已有契约 | 必须保留的可观察结果 | 禁止的 HA 式误套 |
| --- | --- | --- |
| 最新有效数值目标（T31-E） | 新目标先过授权和安全校验；有效才替代旧目标，两次记录可追；无效新目标不覆盖有效旧目标 | 把 `restart` 当撤销协议写；或因 `single` 忽略新目标；或排队执行全部过时目标 |
| 启动中停机（T31-F） | 合法且安全允许时转为停机意图，取消未发送启动，已发送的不假装撤回；按设备能力停机 | 在旧启动序列后排队继续启动，或将停止脚本当作物理停机 |
| 停止中启动（T31-G） | 不自动排队重启；有效状态明确且符合启动条件后，由用户重新确认 | 套 `queued`，停止完成后执行早先点击的启动 |
| 统一所有权／仲裁（T29、T31-B/H） | 人工、规则、状态机共用控制入口；EMS 使用既有仲裁，拒绝及接管有原因，保护继续有效 | 每个自动化各自 `single`，却误认为同设备只有一个写入者 |
| 无隐式重试（T30、T31-D/H） | 超时、重连、恢复自动不重发旧动作；停机作为获准的新操作，不是假定补偿 | 通过重复触发、重新排队或重启执行序列隐式重试 |

“最新有效”不表示跨主体无条件最后写者获胜；同级冲突尚未约定时仍需明确，不靠列表顺序决定。泵启停规则也不无条件推广到所有离散命令。[C §4、T31]

## 3. 至多五项规格建议：只补缺口，用户在原任务中完成

下列路径是 **FastIOT 建议的用户动作**，不是本轮确认过的现有界面。

### 建议 1：分开呈现“本次求值原因”和“首条命中原因”

- **已有覆盖：** C §4 已有行内 AND、首条命中、默认／未命中、行顺序与运行解释。
- **最小采用：** 沿用表格，在一次模拟／运行结果中说明开始求值的来源和时间、命中行、被首行遮蔽的匹配行；明确当前产品的重新求值契约。借 HA trigger 来源及 `choose` 顺序解释，不新增全套 trigger 类型或条件树。[1][2][3]
- **用户路径：** 打开规则草稿 → 填两条同时成立的行 → 模拟 → 看首条与遮蔽原因 → 调换行序再模拟，结果相应改变；无匹配时明确兜底或不提出动作。
- **反例／T 映射：** 只改变非触发输入就假定已执行；两行满足便执行两次；未命中自动置零。纳入 **T29**，不改命中策略。

### 建议 2：补持续／冷却跨中断的生命周期，不增加持久定时系统

- **已有覆盖：** C §4 有持续、冷却及坏值／过期阻断；§5 有重启恢复前核对观测和控制权。
- **最小采用：** 写清起算、重置与恢复的条件，运行解释显示“等待中／已重置／冷却中”。保守候选：连续有效观测中断后重新累计持续时间；这是待确认的 FastIOT 选择，不是 HA 保证。冷却是否保留须单独决定，不能由 `for` 类推。[5]
- **用户路径：** 填持续 30 秒 → 模拟满足 20 秒后重启／重载／坏质量 → 恢复有效输入 → 看计时如何按确定的契约变化，不因旧计时补发动作。
- **反例／T 映射：** 离线 10 秒被算进“连续满足 30 秒”；规则换版沿用旧阈值计时；冷却丢失导致恢复后重复发命令。补 **T29**，恢复与不重放联验 **T30**。在生命周期确认前，不宣称已解决跨重启连续性。

### 建议 3：把 mode 的危险映射变成控制反例，不增加四选一配置

- **已有覆盖：** C §4 统一所有权，T31-E/F/G/H 已明确数值目标替换、泵启停及去重；§5 禁止自动重试。
- **最小采用：** 不新增并发策略功能，只补表格输出进入既有控制链路的交叉验收；将“动作已提出”和“当前有效目标／实际结果”分开。不能以 HA 自动化模式替代平台控制政策。[4]
- **用户路径：** 操作员在设备页看到规则提出的目标 → 合法更新数值目标 → 查看新目标及旧目标被替代原因；另用泵样例分别验证启动中停机、停止中启动。
- **反例／T 映射：** `single` 式丢弃新目标、`restart` 式假撤回、`queued` 式过时启动、`parallel` 式同目标乱写；超时后规则自动重试。覆盖 **T29 + T30 + T31-E/F/G/H**；不另造命令中心。

### 建议 4：沿用 trace 的逐步解释，但把模拟与真实执行严格隔开

- **已有覆盖：** C §4 有模拟零写入、草稿隔离、输入质量与动作结果；§5 和 T31-A/D 已区分独立运行反馈与未知。
- **最小采用：** 规则结果就地展开本次版本、输入及质量、命中／抑制原因、请求及设备反馈关联；复用现有记录，不建另一套流程系统。模拟保持独立执行边界，绝不把 HA **Run actions** 或“模拟触发”作为安全模拟范例。[6][8]
- **用户路径：** 规则草稿 → 输入模拟值并运行 → 看明确仿真结果 → 应用后查看一次真实结果 → 从命中行追到原设备的失败／未知原因。
- **反例／T 映射：** 手工执行跳过条件却声称完整规则验证；模拟事件触发另一条真实规则；写入应答或值回填但无运行反馈仍显示成功；等待超时后继续流程被看作到位。补 **T29/T30/T31-A/D**。

### 建议 5：模板复用仅补验收，不重复新增 blueprint 能力

- **已有覆盖：** C §4 已完整规定类型化输入、显式绑定、单位／目标校验、实例独立及模板草稿隔离。
- **最小采用：** 不追加功能条文；以 HA blueprint 填参路径核对当前交付路径和反例。无需 Take control、共享 YAML 更新或社区模板市场。[7]
- **用户路径：** 选液位报警模板 → 绑定 A 设备和阈值／持续时间 → 保存草稿并模拟 → 明确应用；再建 B 实例，只修改 B 参数。
- **反例／T 映射：** 缺设备时偷偷回退示例对象；改 A 影响 B；改模板草稿静默改变运行版；模拟 A 触发 B；保存等于应用。沿用 **T29**，类型／绑定关联 **T28/T34**。不存在“借鉴 HA 所以这项尚未覆盖”的结论。

## 4. 未知项与停止边界

1. **FastIOT 求值时机未在所读 §4 中定全：** 输入变化、周期、重新启用、换版何时触发计算；条件一直满足时，是每次求值都提出新请求，还是要重新进入／持续门槛才触发。需结合持续、冷却和去重明确，不能用 HA 名称代替契约。
2. **时间生命周期待定：** 持续与冷却跨停用、重启、重载／发布、坏质量的处理；本次只核验 HA state trigger `for`，不推断 HA 所有等待的持久性，也不要求引入定时 helper。
3. **统一仲裁中的同级冲突仍需具体场景约定：** 已有数值目标更新和泵启停规则不再重开讨论，但它们不能回答所有规则／人工／状态机竞争的优先级问题。
4. **设备反馈真实性依赖模型／驱动：** 哪些属性是独立观测、如何判新鲜和关联到本次请求，不由 HA trace 或 `wait_template` 保证；本轮未读取具体驱动源码、未做设备验证。
5. **实现状态未知：** 本轮只对照规格和官网，不证明现有表格支持遮蔽行展示、完整 trace 或模板路径。HA 官网为持续更新文档，未固定发布版／源码 SHA；用于交互与语义借鉴，不承诺复刻其运行实现。

到此停止：不扩展 DMN／FEEL、自由脚本、可视化流程、全量 HA 集成、持久调度或控制重试框架；不直接修改规格与代码。

[2] [Conditions](https://www.home-assistant.io/docs/scripts/conditions/) — 条件全部通过及 General 中 `and`／`or`／`not`／`trigger`。用于条件组合，不据此宣称嵌套编辑是 FastIOT 必需能力。

[3] [Choose](https://www.home-assistant.io/building-blocks/choose/) — 首个条件全满足的候选、可选 default、多个独立 choose，以及 Add option／Add default actions。

[4] [Automation modes](https://www.home-assistant.io/docs/automation/modes/) — single／restart／queued／parallel、条件检查、顺序和并发限制；不是设备所有权协议。

[5] [State trigger](https://www.home-assistant.io/triggers/state/) — Options in YAML 的 `for` 与 Good to know 的 restart／reload 重置说明。未将此推广到所有 HA 计时对象。

[6] [Testing your automation](https://www.home-assistant.io/docs/automation/testing/) — Viewing the traces of an automation、Run actions、Using a simulated trigger to test an automation；真实动作警告与 trace 检查路径。

[7] [Using automation blueprints](https://www.home-assistant.io/docs/automation/using_blueprints/) — 导入、创建实例、输入修改、Take control 以及更新蓝图对既有自动化的影响。

[8] [Wait for a template](https://www.home-assistant.io/building-blocks/wait_template/) — 初始检查、超时、`continue_on_timeout`、`wait.completed`；表达式满足不自动等于独立设备到位反馈。
